问题：组内已经跑过 direct，还需要补一种依赖写法，并检查旧报告会不会继续进入修复。

候选方案：用 macro 或 mixed；只看补丁，或者把构建、修复和复验一起跑一遍。

兼容性与测试：E11 没改原有修复代码。新增三项测试，连同原测试共 13 项通过；正常场景和两个旧报告场景也实际运行过。这里只测了单个目标使用 DEPS 的情况，没有测多个目标共用变量。记录在 work/e11-b-231880393-20261115/。

## E12：检查报告类型和重启后的任务

编号、日期、作者：E12-231880393-02；2026-11-15；肖天纵。

问题：消费报告时没有指定期望的 kind，类型错误没有及时拦住。还需要检查 API 的重复提交、下载和重启结果。

候选方案：只测 check_envelope，或者在实际消费报告的位置补检查。任务失败后可以继续用旧键查询，也可以换新键重新提交。

采用方案与原因：在 pipeline.execute 中按 mode 传入期望类型，E11-B 用 fixed-md，E12 用 incremental-check。这样类型错了就先停下来，不继续做补丁。旧键保留原任务，重新运行用新键，避免一次提交对应多个任务。

输入输出字段：五阶段共用 job_id/trace_id；full-check 对应 base，其他阶段对应 target。repair 的 input_report 必须指向本轮增量报告，URI 和哈希都要对上。文件下载同时核对清单、响应头和文件哈希。重启前没返回 trace_id 的中断任务留空。

兼容性与测试：没改 HTTP 路由、server.py 和 lab.py。新增三项测试，总数 16 项，全部通过。真实 CLI/API 运行检查了下载、重试和重启。Windows 经 SSH 访问 Linux 的结果已保留，但还没有 A 组同学参与交接，双方联调和真实项目验收都未完成。记录在 work/e12-231880393-20261115/。
